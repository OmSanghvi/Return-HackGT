Draw It. Step Inside It. — Updated Full Build Guide
This is the version I would actually build for HackGT.
The biggest changes from the original guide are:
No Quest dependency. Build and demo on a laptop/desktop first.
NemoClaw becomes the agent/orchestration layer, rather than something that directly performs the reconstruction.
Notability is the input surface, but don't depend on live Notability automation.
Nano Banana is optional preprocessing, not a required step.
SAM 3 + SAM 3D are the reconstruction pipeline.
Nebius GPU and Nebius Token Factory remain separate.
Unity is the 3D runtime, but initially runs as a desktop application.
The backend owns the scene schema. Unity never directly talks to the AI models.
SAM 3D is not forced onto diagrams. For diagrams, use semantic objects/primitives when appropriate.
Everything has a fallback, so one broken API doesn't kill your demo.
The original guide already established the important separation between Nano Banana, SAM 3/SAM 3D, Nebius GPU, Token Factory, Blender, and Unity.

3. The stack
Frontend / input
Notability
Use it for:
drawing
annotating
writing instructions
exporting the sketch
Do not build live handwriting streaming.
The original guide correctly recommended exporting/sharing the page rather than trying to stream Notability continuously.

Agent
NemoClaw
Use NemoClaw as:
"The computer-use/orchestration brain."
It should be able to call your controlled tools:
capture_sketch()
analyze_sketch()
reconstruct_scene()
get_scene()
modify_scene()
spawn_object()
set_transform()
refresh_unity()
send_to_unity()

NemoClaw does not replace Unity as the game runtime. Instead, it should use a controlled Unity MCP bridge to orchestrate the existing desktop world.

Unity owns the runtime behavior:
- WASD movement
- mouse look / camera controller
- ground and lighting
- world state and rendering
- player interaction

NemoClaw owns orchestration:
- capture the sketch
- interpret the user instruction
- call the reconstruction pipeline
- fetch the current scene
- modify scene objects or transforms
- push the update to Unity through a safe tool layer

This is the key separation for the build: Unity remains the live 3D runtime, while NemoClaw orchestrates scene creation and scene edits through controlled MCP tools rather than directly owning the gameplay layer.

Don't give the agent unrestricted computer access.
NemoClaw currently creates sandboxed OpenClaw environments and supports controlled inference providers and policies. (NVIDIA Docs)
NVIDIA NemoClaw documentation

Unity MCP bridge
The Unity MCP bridge should expose only safe, bounded actions to NemoClaw, for example:
- get_scene()
- list_objects()
- spawn_object(type, position, scale)
- set_transform(object_id, position, rotation, scale)
- add_light()
- refresh_unity()

The backend still owns the shared scene schema. Unity does not talk directly to every model; it consumes the scene representation and updates the live world based on validated scene JSON.
This keeps the agent deterministic and means one broken AI component does not crash the runtime.

4. AI layer
Gemini / Nano Banana
Use this only if it improves the input.
Current Gemini documentation describes Nano Banana as Gemini's native image-generation/editing capability, including image-to-image editing. (Google AI for Developers)
Your prompt could be:
Clean this hand-drawn sketch into a simple concept image.

Preserve:
- object identity
- object count
- relative positions
- approximate proportions
- spatial relationships

Remove:
- handwriting noise
- accidental strokes
- paper texture

Do not add new objects.
Do not change the composition.
Then compare:
raw sketch → SAM 3 → SAM 3D

vs.

raw sketch → Nano Banana → SAM 3 → SAM 3D
If Nano Banana makes the result worse or too slow:
remove it.
The original plan explicitly treated this as a bake-off rather than assuming it would improve reconstruction.

7. Important: don't use SAM 3D for everything
This is one of the biggest changes I'd make to the original idea.
Suppose someone draws:
      ↑ F
       │
       ●
       │
       ↓ mg
You don't really want SAM 3D to reconstruct that.
You want:
circle → sphere
arrow → vector
text → label
line → axis
So your backend should have two reconstruction modes:
Mode A — physical object

 ↓
SAM 3
 ↓
SAM 3D
 ↓
3D asset
Mode B — semantic diagram
sketch
 ↓
vision model
 ↓
semantic scene
 ↓
Unity primitives
This makes your system much more robust.

8. Nebius GPU
The Nebius GPU is where you run the expensive model workloads.
Conceptually:
FastAPI
   │
   │ request reconstruction
   ▼
Nebius GPU VM
   │
   ├── SAM 3
   ├── SAM 3D
   └── PyTorch / CUDA
   │
   ▼
.glb
Nebius currently provides GPU VMs intended for AI workloads, including on-demand and preemptible instances. (Nebius)
Nebius GPU Compute
Do not confuse this with Token Factory.

9. Nebius Token Factory
Token Factory is your:
reasoning / classification / structured-output layer
not your SAM 3D GPU.
Nebius describes Token Factory as an OpenAI-compatible inference API for open models. (Nebius)
Nebius Token Factory
Give it:
{
  "objects": [
    "house",
    "tree",
    "sun"
  ],
  "text": [
    "make tree twice as tall"
  ]
}
And require:
{
  "action": "transform",
  "target": "tree_1",
  "operation": "scale",
  "value": 2.0
}
Never let the model directly send arbitrary Unity commands.

10. Your shared scene schema
This is the most important piece of the entire architecture.
Create:
shared/
    scene.schema.json
Start with:
{
  "objects": [
    {
      "id": "house_1",
      "type": "house",
      "position": [0, 0, -3],
      "rotation": [0, 0, 0],
      "scale": [1, 1, 1],
      "asset": "house_1.glb",
      "source": "sam3d"
    }
  ],
  "instructions": [],
  "transform": {
    "theme": "none"
  },
  "meta": {
    "source": "notability",
    "preprocessed": false
  }
}
Then an instruction:
{
  "target": "tree_1",
  "action": "scale",
  "value": [1, 2, 1]
}
Everything talks through this.
